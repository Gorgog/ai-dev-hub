# Замок диспетчера: суд по программе

Замок тяжёлых и средних ресурсов (`plugin/skills/dispatch/scripts/guard.cjs`) блокирует вызов в worktree проекта
без гранта, если вызов подходит под правило `dispatch-rules.json` проекта. С среза 15 Bash-команда сверяется с
правилом не по тексту, а по программам, которые она реально запустит. Формат `dispatch-rules.json` не изменился.

## Как судит

1. `shell.cjs` (`executions(cmd, { cwd })`) разбирает команду: списки, конвейеры, `( )`, `$( )`, `` ` ` ``, `<( )`,
   присваивания и `export` (переменные подставляются, без кавычек делятся на слова), `cd`, `source`. Текст в
   кавычках, тела heredoc, комментарии, шаблоны `case`, списки `for … in` и `[[ ]]` — данные, не программы.
   Ветвления не прослеживаются: каждая ветка считается запущенной.
2. Обёртки раскрываются до того, что они запускают: `env`, `timeout`, `nice`, `nohup`, `sudo`, `time`, `exec`,
   `command`, `xargs`, `find -exec`, `watch`, `flock`, `dotenv`, `cross-env`, `env-cmd`, `hub-run.sh … --`,
   `docker exec|run`, `docker compose exec|run`, `bash|sh -c`, `eval`, `bash -s <<EOF`. Пакетные раннеры
   (`npx` с ключами, `pnpm exec|dlx`, `yarn dlx|exec`, `bunx`, `npm exec`) и `node …/node_modules/<пакет>/bin/…`
   дают бинарь пакета. Скрипты с диска (`bash f`, `./f`, `source f`) читаются, `$@` — аргументы вызова; глубина
   ≤ 3, файл ≤ 256 КБ. JS-скрипты не читаются: программа — сам скрипт (`node polygon/run.cjs …`).
3. Каждая программа даёт строки для правила: `ИМЯ=знач … программа аргументы`; бинарь пакета ещё и
   `npx <бинарь> …`; запуск скрипта пакета через npm/pnpm/yarn/bun ещё и `npm run <скрипт> …`. Аргументы с
   пробелами (сообщения, шаблоны, строки кода) маскируются `''`.
4. Совпадение засчитывается, только если держится на программе: та же ветка регэкспа (по верхнему `|`) не должна
   совпадать со строкой, где слово программы заменено на `_`. Так `grep "npx jest"`, `git commit -m "kubb generate"`,
   `sed … backend-all-batches.sh` не блокируются, а `npx --yes jest`, `node node_modules/jest/bin/jest.js`,
   `bash scripts/test.sh` (внутри `npx jest`) — блокируются.
5. Не разобрал (незакрытая кавычка) или программа известна только при запуске (`$RUNNER x`, `eval "$X"`,
   `… | bash`) — правило проверяется по тексту всей команды, как раньше.

Причина блока называет программу (`Программа: npx jest …`); журнал `dispatch-guard.log` пишет `by` (`program` /
`text`), `program` или `fallback`.

## Выкат и откат

Два модуля под одним обработчиком `lock` (бюджет обработчиков не растёт): `pretool.d/10-lock.cjs` — по тексту (v1),
`pretool.d/11-lock-program.cjs` — по программе, запись `plugin/mechanisms/lock-program.json`. Судит ровно один:
где lock-program включён своей стадией, `10-lock` уступает.

- Стадия `canary` — включён только в проектах, чей `projects/<имя>/canary.json` перечисляет `lock-program`;
  ступени: проект хаба → проект B → `on`.
- Откат — стадия `off` в `lock-program.json` (сразу, без перезапуска): снова судит `10-lock` по тексту.
- Ошибка разбора внутри `11-lock-program` — решение по тексту; ошибка и там — пропуск, как у `10-lock` и v1.

## Что знать, составляя правила

- Правило по-прежнему регэксп; пишите его про запуск (`npx\s+jest\b`, `npm\s+run\s+dev\b`), обходы ключами,
  обёртками и переменными замок ловит сам.
- Правило, которое называет программу целиком (`\bnode\s+\S*snippets/…`), блокирует любой запуск этой формы —
  и пробу, и утилиту из той же папки: такое сужают в правиле проекта.
- Скрипт пакета (`npm run lint`) не раскрывается в свои команды из `package.json`.
