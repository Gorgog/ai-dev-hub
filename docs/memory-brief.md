# Хуки хаба: бриф на старте сессии

Бриф SessionStart — то, что сессия проекта получает в контекст до первого вопроса: проект, ветка, предполётная
проверка, правила из ошибок и «Дальше» последней заметки своей ветки. Вместе с файлами `CLAUDE.md` он и есть
постоянный контекст на старте (acceptance §3: v1 ≈ 49 КБ, цель ≤ 30 КБ). Библиотека — `plugin/hooks/session-start.cjs`.

## Два модуля, один обработчик `memory-brief`

| Механизм | Модуль | Стадия | Что подаёт |
|---|---|---|---|
| `memory-brief` | `sessionstart.d/10-memory-brief.cjs` | on | индекс `memory/errors-index.md` в бюджете брифа (`brief.json` `indexSections` — нужные разделы целиком, остальные строкой «по касанию») |
| `memory-core` | `sessionstart.d/09-memory-core.cjs` | canary | память v2: ядро уроков вместо индекса (срез 29) |

На каждом старте бриф ровно один. `memory-core` идёт раньше и подаёт бриф, если раннер его запустил (стадия `on` или
`canary` с id `memory-core` или обработчиком `memory-brief` в `projects/<имя>/canary.json`), в событии есть `cwd`, у
проекта есть `memory/lessons/` и та же проверка канарейки (`session-start.cjs` `coreOn`) сходится. Событие, для
которого он подал бриф, он отмечает (`coreGiven`), и `memory-brief` отходит в сторону только для отмеченного события.
Решение одно (ревью 1): раннер пропустил модуль ядра (нет `cwd`, канарейку поменяли между чтениями) или модуль упал —
события без отметки, бриф даёт `memory-brief` по индексу; двух брифов и старта без брифа не бывает. В проекте без
`memory/lessons/` и вне канарейки бриф — прежний, побайтно.

## Бриф ядра (память v2)

```
Бриф хаба: <проект> · ветка <ветка> · изменённых N · хаб <sha>
Предполётная проверка: …                       (если есть что сказать)
Ядро уроков (memory/lessons/, status core) — действует всегда:
- <первая строка урока> [<id>]                 (≤ 15 строк)
Ядро сверх 15 — по касанию: <id>, <id>         (если уроков ядра больше)
По касанию — ещё N уроков: урок с триггером `when` хук подаёт при касании темы, любой — /hub:recall. …
Последняя заметка этой ветки: memory/sessions/<файл>   (в рамке «данные из памяти»)
```

- Ядро — уроки `status: core`: фазо-независимые правила, нужные в любой сессии. Порядок: класс «одного раза»
  (`kind: once`), затем правила, знания; внутри — по дате `created` и id. Строка — первая строка урока (≤ 160 знаков) и
  его id, чтобы `recall` и счётчик повторов находили урок.
- Лимит ядра — 15 строк (решение 06.11). Штатно ядро держится в 15 (перевод памяти и `/hub:memory-gc`); строка
  «Ядро сверх 15 — по касанию: <id>, …» — защитная: первые 15 строками, остальные id одной строкой, в предполётной
  проверке — готовая команда `node '<плагин>/skills/memory-gc/scripts/gc.cjs' --memory '<проект>/memory' core`:
  кандидаты на вынос в active по решению (г) — урок ядра (не класс «одного раза»), чей триггер `when` принимает
  проверка записи и видит хук уроков (событие из `plugin/mechanisms/memory-lessons.json`, инструменты — матчер этого
  события в `plugin/hooks/hooks.json`), с причиной у каждого; перенос — `gc.cjs core --apply <id>…` после «да»
  (скилл `memory-gc`, шаг v2-д). Класс «одного раза» без такого триггера и урок с триггером только на вызовах, которых
  хук не слушает (MCP, Agent на 06.11), остаются в ядре. Новый `once` с рабочим триггером wind-down
  (`episode.cjs add`) сразу кладёт в active, без него — в ядро: слой ставит скрипт, не черновик. Внимание: за порог уходят по виду и дате, не по
  наличию триггера — урок ядра без `when` (или с триггером, который не срабатывает) из строки id сам не придёт, его
  найдёт только `/hub:recall`; поэтому предупреждение в предполётке надо разбирать, а не терпеть. Не влезает в бюджет
  брифа (9500 знаков с заметкой) — последние строки ядра тоже уходят в строку id.
- Уроки `status: active` в бриф не идут: урок с триггером `when` подают модули памяти v2 при касании
  ([memory-hooks.md](memory-hooks.md)), урок без триггера находит только `/hub:recall`. `retired`/`superseded` — архив.
- В ядро и в счёт «по касанию» идут только уроки, которые принимает проверка записи (`validateLesson`), — как и в
  триггеры (`store.ensureTriggers`): файл, записанный мимо хука (источник «внешний» в любом регистре, команда пуша или
  URL в тексте, NUL, битый frontmatter), правилом хаба не подаётся; порчу называет `memory-check`.
- Ядро, как и индекс, — правила проекта, без рамки; заметка ветки — данные из памяти, в рамке (решение 05.11,
  [delivery.md](delivery.md)).
- `memory/errors-index.md` в памяти v2 — выводимый экспорт (`recall export-v1`); бриф говорит его не читать.

## Двойное чтение

До среза 29 шаблон `CLAUDE.md` проекта велел «в начале сессии прочитать `errors-index.md` целиком» и «прочитать
последнюю заметку», хотя бриф уже нёс и то и другое: по журналам v1 28 из 68 сессий задач читали индекс ещё раз
(Read). Шаблон теперь говорит: правила и «Дальше» — в брифе, не перечитывать; остальное — по касанию и `/hub:recall`.
У уже созданных проектов эти строки `CLAUDE.md` правятся при выкате (память проекта правит диспетчер).

## Тематические правила (проба P5)

`.claude/rules/<тема>.md` с `paths:` Claude Code грузит по касанию пути только из корня репозитория или worktree
(`repo/.claude/rules`) и из `~/.claude/rules`; из `projects/<имя>/.claude/rules` и корня хаба — не грузит (P5,
05.11). Поэтому правило одной темы проекта — урок памяти с `when: path` (подаётся при касании; решение
06.11, папки `templates/project/.claude/rules/` нет). `.claude/rules/<тема>.md` с `paths:` — только в `repo/`, если
репозиторий свой.

## Включение и откат

- Включить на проекте: `memory-core` в `projects/<имя>/canary.json` (делает диспетчер, по стадиям: хаб → проект B →
  все). Действует с нового старта сессии.
- Откат: убрать `memory-core` из `canary.json` (сразу) или `"stage": "off"` в `plugin/mechanisms/memory-core.json`;
  тогда бриф снова подаёт `memory-brief` с индексом.
- Проверки: `node --test plugin/hooks/memory-core.test.cjs`, полигон `--level hook --only '^H53'`.
