# Цикл улучшения: недельный аудит процесса

Раз в неделю хаб сам смотрит, как шла работа, и делает обратимое по правилу; пользователю — итог недели одним
сообщением и вопросы только о необратимом (срез 24). Циклы — скриптами, без отдельного прогона модели.

## Как запускается

Модуль `plugin/hooks/sessionstart.d/50-improve.cjs` (handler `improve`, запись `plugin/mechanisms/improve.json`) на
старте основного потока (`startup | clear`):

- прошла неделя с прошлого запуска и прогона нет — запускает `tools/process-audit/weekly.py --refresh --apply
  --polygon` в фоне под `hub-run.sh` (потолок 2G, таймаут час); старт сессии не ждёт;
- прогон дописал итог — подаёт его один раз (`info`, ключ `improve`); прогон кончился без итога — говорит об этом
  один раз;
- иначе молчит. Компакция, `resume`, субагент — молчит.

Данные — `HUB_DATA`, иначе `~/hub-data`, и только если это копия этого хаба (все проекты хаба есть в её
`hub/projects`) с базой вызовов: хаб полигона или теста реальную копию не обновляет. Состояние —
`<данные хуков>/improve/state.json`, итог — `improve/week.json`. Стадия `canary` → проект хаба → проект B → все;
откат — стадия `off` (сразу) или revert + sync.

## Что считает (`weekly.py`)

```
python3 tools/process-audit/weekly.py --data ~/hub-data --dry-run          # итог на снимке, ничего не пишет
python3 tools/process-audit/weekly.py --data ~/hub-data --hub <хаб> --events <данные хуков> --apply
python3 tools/process-audit/weekly.py --data ~/hub-data --hub <хаб> --events <данные хуков> --revert <id>
```

Окно — 7 дней до последнего вызова копии (`--until`, `--days`). По окну:

- **метрики §3** приёмки (`tools/analytics/metrics.py`) и тренд: строка недели в `<data>/process-audit/trend.jsonl`,
  итог показывает изменение к прошлой неделе;
- **нарушения правил** по разбору shell (`depth/shell-rules.cjs`);
- **кластеры провалов** — упавшие вызовы по тому, что запускалось: обёртка (`timeout`, `hub-run.sh`), подготовка
  (`cd`) и фильтр (`| tail`) — не программа;
- **ворота пуша диспетчера** (условие 27, H09): пуш через `push-slice` — с воротами; голый `git push` без запуска
  `parallel-check` раньше в той же сессии — пропуск. Считается запуск, не упоминание;
- **действенность**: правила rules-guard — повтор по вызовам окна (напоминание открывает окно из 3 следующих вызовов
  эпохи: правило снова — «повтор», нет — «предотвратил»); уроки — счётчик журнала подачи (`docs/delivery.md`); уроки
  памяти v2 — показы и повторы.

## Что делает сам (обратимо, `--apply`)

| Действие | Когда | Откат |
|---|---|---|
| повысить правило проекта на ступень `log → deny-once → deny` (`modes` в `projects/<имя>/rules.json`) | ≥ 5 окон и «предотвратил» < 50 %; окна до прошлого повышения не считаются | `--revert <id>` |
| урок v2 в отставку (`store.retire`) | его условие отставки: 30 дней без показа и повтора; класс «одного раза» — никогда | `--revert <id>` (статус `active`, событие `restored`) |
| кандидат-сценарий полигона | урок v1 с «механизм: нет» повторился — заготовка в `<data>/process-audit/candidates/` | удалить файл |
| кандидат в правило (правило 7) | второй похожий эпизод: v1 — повторов ≥ 2 без механизма, v2 — урок-знание повторился | — (список) |

Каждое действие и вопрос — строка журнала событий подачи (`<данные хуков>/events/<ГГГГ-ММ>.jsonl`, `mode: improve`,
свой `id`); кандидат — один раз за всё время, вопрос — раз в неделю, пока не решён.

## Что только спрашивает (необратимое)

- шаг к `deny`, когда правило срабатывает чаще 1 раза на 100 Bash-вызовов проекта: сузить правило или `ask`;
- урок «одного раза» повторился — нужен механизм.

## Разбор shell аналитики

`tools/analytics/shell-read.cjs` — читатель замка (`plugin/skills/dispatch/scripts/shell.cjs`) для команд из
журналов: без диска (скрипт, названный в старой команде, — не файл на диске сейчас), `$((` без своей `))` —
подоболочка. Через него читают `shell-flags.cjs` (06), `depth/shell-rules.cjs` (11) и цикл улучшения.
