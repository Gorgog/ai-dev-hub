Оркестр без споров

Как организовать разработку на Claude Code так, чтобы ИИ вёл проект по этапам, помнил всё между сессиями и проверял сам себя. Главная поправка к исходной идее: «оркестр спорящих ИИ» — миф; наука и практика 2025–2026 сходятся на другой схеме — независимая генерация + исполнение тестов как арбитр + ревьюер с чистым контекстом.

Сводка параллельного исследования: память, оркестрация, методологии, верификация, альтернативные инструменты, практики тяжёлых пользователей.

Фактчек: дают ли «спорящие ИИ» лучший результат?

Проверено по ≥10 научным работам 2023–2026. Уверенность вывода: высокая.

Миф

Свободные дебаты агентов до консенсуса. Контролируемые исследования (Debate or Vote, Stop Overvaluing MAD, Should we be going MAD?) показывают: при равном бюджете токенов дебаты не обгоняют обычное «сгенерировать N ответов и проголосовать». Хуже того — точность может падать от раунда к раунду: агенты меняют правильный ответ на неправильный под «давлением группы» (сикофантия). Стоимость — 16–25× токенов за околонулевой прирост.

Работает

Исполнение кода как арбитр. У кода есть то, чего нет у споров, — объективная проверка. Тесты и запуск кода — самый воспроизводимый механизм прироста качества: AlphaCodium (19% → 44% на CodeContests), AgentCoder (96.3% HumanEval при меньшем расходе токенов), CodeT (+18.8 п.п.). Ключевая деталь AgentCoder: тесты пишет агент, который не видел реализацию.

Работает

Асимметричная критика вместо симметричного спора. Один ревьюер, которому явно велено «опровергни / найди баги», с чистым контекстом (не видит рассуждений автора) — ловит ~2 бага на PR, 58% серьёзных (Cognition). CriticGPT-подход: критик находит больше багов, чем платные ревьюеры-люди. Итог спора решают тесты или человек, а не «договорённость» агентов.

Узкая ниша

Структурированные дебаты гетерогенных моделей. Единственное место, где дебаты окупаются: архитектурные решения без «исполняемого оракула», разные вендоры моделей (Claude + GPT), спор строго вокруг конкретных улик, мало раундов, независимый судья. Ожидание: единицы процентов прироста за ~10–25× токенов.

Правило: лишние вычисления тратьте на проверку (тесты, запуск, чистый ревью), а не на разговоры (дебаты, консенсус, ролевые игры). Ни один достоверный результат, обгоняющий одну сильную модель, не получен за счёт того, что агенты «уговорили» друг друга.

Память: чтобы ИИ помнил всё между сессиями

Главный инсайт: сложность не в хранении, а в извлечении. Дисциплинированный markdown в git обгоняет «стартапы памяти».

Три слоя, покрывающие ~95% потребности

  1. Нативная база (бесплатно, уже встроено). Короткий CLAUDE.md в корне проекта (<200 строк — дальше правила начинают игнорироваться) + .claude/rules/*.md с привязкой к путям + личный ~/.claude/CLAUDE.md. Автопамять Claude Code включена по умолчанию: он сам ведёт заметки в ~/.claude/projects/<проект>/memory/. Периодически ревизуйте через /memory. Ключевой ритуал (Boris Cherny, создатель Claude Code): каждый раз, когда ИИ ошибся — правило в CLAUDE.md, чтобы не повторял.
  2. Git как долгая память. docs/decisions/ — журнал решений («выбрали X, отвергли Y, потому что…») — не даёт заново пересматривать решённое. Скилл «завершение сессии», пишущий docs/sessions/ГГГГ-ММ-ДД.md (контекст, решения, открытые вопросы, следующие шаги) — новая сессия начинает с чтения последнего. Структурированные сообщения коммитов — git log становится базой знаний. Для длинных бэклогов — Beads (git-трекер задач, спроектированный для агентов).
  3. Автоматический «тотальный отзыв» — только если реально нужен. claude-mem (~92 тыс. звёзд, локальный SQLite): пишет всё через хуки, сжимает, даёт поиск «что мы решили про биллинг три недели назад». Облачные (mem0 и пр.) — скепсис: независимый замер дал 49% против заявленных 91.6%, плюс ваш код уезжает в чужое облако.

«Compound engineering» (Every): после каждой задачи — минута на «кодификацию»: чему научились → в CLAUDE.md / скилл / журнал решений. Каждая фича делает следующую дешевле. Это и есть «ИИ учится на проекте» — не магия, а ритуал.

Оркестрация: какой паттерн для какой работы

Anthropic и Cognition независимо пришли к одному: один главный цикл держит состояние; сабагенты — узкие, без записи в код, возвращают выжимку.

Конвейер: этапы, которые снимают работу с вас

Spec-driven development — консенсус 2026: источник истины — версионируемая спека, а не переписка в чате.

  1. Идея → Спека«Проинтервьюируй меня по фиче X, копай в сложные места, потом запиши полную спеку в SPEC.md». Спека обязана включать требования к авторизации/безопасности (дыры вайбкодинга живут в спеке, не в коде) и финальный сценарий проверки. Тяжёлый вариант — GitHub Spec Kit (constitution → specify → plan → tasks → implement).
  2. Спека → ПланСвежая сессия, план-режим (Shift+Tab): ИИ читает кодовую базу read-only и пишет план. Вы правите план, а не код, — здесь ваши 15 минут дают больше, чем часы правок потом. Cherny: план-режим «легко удваивает-утраивает» результат на сложных задачах.
  3. План → ЗадачиМелкие задачи с зависимостями; правило размера: одна задача = один контекст + проверяемый итог. Инструменты: Spec Kit tasks, Taskmaster (parse-prd), Beads для многодневного бэклога.
  4. Реализация (TDD-цикл)На задачу: падающий тест → коммит теста (иначе агент может «подогнать» тест — коммит делает это видимым в диффе) → реализация до зелёного → рефакторинг → коммит. Данные: упрощённый агентный TDD поднимал решаемость с 12% до 50% (TDFlow). Параллельные фичи — claude --worktree.
  5. ВерификацияРевьюер с чистым контекстом + /code-review + security-скан + E2E-доказательства (скриншоты, консоль), не «код выглядит верно». Подробно — пирамида ниже.
  6. Отгрузка + КодификацияPR через git (откат всегда возможен), CI гоняет те же проверки. Затем — уроки сессии в CLAUDE.md/скиллы. Цикл замкнулся: проект «учится».

Автономные циклы («Ralph») — while true; claude -p PROMPT.md — работают только для точно специфицированной работы, в песочнице (контейнер обязателен), с тестами как воротами и лимитом итераций. На неоднозначной задаче цикл ухудшает код с каждым проходом и жжёт $50–100 за ночь.

Конкретный сетап: что положить в репозиторий

Всё нативное, коммитится в git, одинаково работает локально, в облачных сессиях и в CI. Тяжёлые сторонние фреймворки (Claude Flow, SuperClaude) сообщество признало избыточными — Anthropic впитала их ценность в продукт.

репозиторий/
├── CLAUDE.md                  # <200 строк: стек, команды, жёсткие правила
├── docs/decisions/            # журнал решений (почему X, а не Y)
├── docs/sessions/             # итоги сессий (пишет скилл «wind-down»)
├── .github/workflows/claude.yml  # @claude в PR + авторевью каждого PR
└── .claude/
    ├── settings.json          # хуки + разрешения (коммитится)
    ├── agents/
    │   ├── architect.md       # read-only, план-режим, сильная модель
    │   ├── implementer.md     # полные инструменты, память проекта
    │   ├── reviewer.md        # ТОЛЬКО Read/Grep/Glob — обязан докладывать,
    │   │                      #   а не чинить сам; настроен опровергать
    │   └── tester.md          # Bash+Read: гоняет тесты, докладывает дословно
    ├── skills/
    │   ├── feature/           # /feature: архитектор→план→код→ревью→тесты
    │   ├── wind-down/         # итог сессии → docs/sessions/
    │   └── ship/              # коммит+PR только при зелёных воротах
    └── hooks/                 # см. ниже

Хуки — детерминированные ворота (CLAUDE.md — совет, хук — закон)

  • PostToolUse на Edit/Write: автоформат + прогон тестов затронутого файла; ошибки попадают агенту в контекст — он сам чинит.
  • PreToolUse: блок правок .env, локфайлов, миграций; блок опасных команд.
  • Stop-хук — «определение готовности»: агент не может завершить ход, пока сборка/линт/тесты не зелёные. Убирает целый класс «я всё сделал» без доказательств.
  • SessionStart (после компакции): заново вбросить критические правила — компакция их иначе теряет.

Пирамида верификации: не читая каждую строку

Зачем: ~45% ИИ-кода содержит уязвимости OWASP (Veracode, не меняется два года); половина выигрыша скорости съедается переделкой (Stanford, 100 тыс. разработчиков). Проверка — настоящее узкое место, не генерация.

  1. L0Среда: песочница/контейнер, git-worktree для рискованного; «YOLO-режим» только внутри контейнера.
  2. L1Хуки на каждый эдит: строгий тайпчек + линт + Stop-ворота «до зелёного». Бесплатно, миллисекунды.
  3. L2Тесты, которые агент обязан пройти, а не свободно пишет: вы утверждаете замысел тестов; property-based тесты для инвариантов.
  4. L3Мутационное тестирование (еженедельно, на рисковых модулях): ловит «лгущие тесты» — 100% покрытие при 61% реальной силы — известный кейс.
  5. L4Security-статанализ каждый PR: Semgrep + security-review. Не обсуждается при 45% базовой частоте уязвимостей.
  6. L5Один малошумный ИИ-ревьюер PR, которого вы реально читаете. Один настроенный лучше двух шумных — усталость от ложных срабатываний глушит ревьюеров за месяц.
  7. L6Кросс-модельное второе мнение — только на рисковых изменениях, только read-only. Важна асимметрия (arXiv 2607.21656): сильная модель ревьюит слабую (+18 п.п.); слабый ревьюер сильного автора ухудшил код (−8.6 п.п.). Патчи ревьюера не применять автоматически.
  8. L7E2E-доказательства: агент прогоняет реальный пользовательский сценарий в браузере (Playwright MCP), артефакты — скриншоты/консоль/сеть.
  9. L8Вы — выборочно: форма диффа (дубли, пропущенные крайние случаи), замысел тестов, и всё, что трогает авторизацию/деньги/удаление данных — руками, всегда.

Практики тяжёлых пользователей

Сжато из ~40 первоисточников: доки Anthropic, Cherny, команды Anthropic, incident.io, Willison, Ronacher.

Делать

  • Дать ИИ способ самопроверки — «стоит 2–3× качества» (№1 у всех).
  • План до кода на всё нетривиальное; правьте план, не результат.
  • /clear между несвязанными задачами; контекст — самый дефицитный ресурс.
  • Правило двух ошибок: две неудачные поправки → /clear и новый промпт с учётом выученного.
  • Показывать образец: «сделай как таблица users» вместо абзацев описаний.
  • Вставлять сырые логи ошибок, не пересказывать словами.
  • Параллель — через worktree, но не шире вашей способности проверить слияние.
  • Автономность по риску: авто-принятие для периферии, надзор для ядра.

Не делать

  • Сессии-«свалки» из несвязанных задач.
  • Спираль поправок в деградировавшем контексте.
  • Верить «готово» без тестов и доказательств — уверенно-неправильное дороже явно сломанного.
  • CLAUDE.md на 400+ строк — правила игнорируются.
  • Отдавать ИИ архитектурные решения — их держит человек у всех сильных команд.
  • Гигантские непросмотренные диффы.
  • Куча MCP-серверов «на всякий случай» — тихо съедают контекст.
  • Наводящие вопросы («правда же хорошо?») — получите поддакивание.

Есть ли решение лучше Claude Code?

Короткий ответ: как хаб оркестрации — нет; но дополнить стоит.

Claude Code остаётся лучшей базой по структурным причинам: самые глубокие примитивы оркестрации (сабагенты, хуки, скиллы, workflows, worktrees, headless/CI), и лидерство на самом трудном агентном бенчмарке (Terminal-Bench 3.0: 42.7% против 34.6% у GPT-5.6). На насыщенных бенчмарках (SWE-bench ~96%) разницы между лидерами уже нет.
