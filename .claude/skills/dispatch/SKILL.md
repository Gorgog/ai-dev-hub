# Диспетчер многосессионной работы

Эта сессия — **диспетчер**. Код она не пишет и в коде не копается. Разведку для нарезки делает один subagent
`explorer`: «какие модули и файлы трогает каждый кусок». Состояние живёт в файлах, а не в разговоре: диспетчера
перезапускают.

`<хаб>` — корень хаба, папка, в которой лежит этот `.claude/`. Скрипты — `<хаб>/.claude/skills/dispatch/scripts/`.
Готовые команды с путями проекта — в его профиле.

| Файл | Что в нём |
|---|---|
| `<хаб>/projects/<имя>/dispatch-profile.md` | профиль проекта: пути, тяжёлое и среднее, горячие точки, пуш, запрещённые сессиям скиллы. Нет профиля — создать с Georgy по `<хаб>/templates/project/dispatch-profile.md` |
| `<хаб>/projects/<имя>/memory/dispatch.md` | доска: сессии, ресурсы, очередь, квитанции, ждущие ответы. Формат — `board-template.md` рядом |
| `slicing.md` (рядом) | как резать задачу на срезы, чтобы часть шла параллельно; git-рецепты для веток срезов |
| `brief.md` (рядом) | шаблон брифа сессии задачи |
| `scripts/` (рядом) | `wt-new.sh`, `wt-remove.sh`, `parallel-check.sh`, `headroom.ps1` |

## 0. Старт и перезапуск

1. Прочитать профиль, доску, шапку `memory/branches.md` и `mcp__ccd_session_mgmt__list_sessions {"linked": true}`.
2. Сверить доску с реальностью:
   - какие сессии живы;
   - кто держит ресурсы;
   - чья миграция стоит в дев-БД.

   Если держатель завершился — см. §4, п. 5.
3. Доложить Georgy в 3–5 строк: сессии, ресурсы, очередь, кто ждёт его ответа.

## 1. Режим задачи: спросить ВСЕГДА

На каждую новую задачу от Georgy — сначала вопрос, даже если задача мелкая.
1. Задачу из трекера читает subagent: полностью, по правилам проекта. Он же смотрит код вокруг и возвращает
   выжимку — объём, модули, развилки. Сам диспетчер вложения и видео не читает: его контекст должен оставаться
   лёгким.
2. Оценить по `slicing.md`: сколько срезов, какие пойдут параллельно, что упрётся в очередь, выигрыш по времени.
3. `AskUserQuestion`: «Одна сессия» / «Многосессионно (N срезов, M параллельно)». Мелкую (один модуль, до
   полудня работы, параллелить нечего) рекомендовать одной сессией.

«Одна сессия» → одна сессия задачи по брифу (шаг 3), без нарезки. «Многосессионно» → шаг 2.

## 2. Нарезка (только многосессионно)

1. Первая сессия — **планировщик**. Она в своём worktree пишет план скиллом `workplan new` (`plan.md` и файл на
   каждый срез с `blocked-by`) и размечает волны по `slicing.md`: касания, горячие точки, хребет, волны. На этом
   она останавливается и докладывает таблицу волн.
2. Показать Georgy таблицу волн: срез → волна → касания → база ветки → цель MR. Без его «да» сессии срезов не
   запускать.
3. Хребет (срез-контракт, если он есть) обычно берёт сама сессия-планировщик: контекст плана у неё уже есть.

## 3. Запуск сессии задачи

**Слово запуска** — «да» Georgy на задачу или на таблицу волн, либо «запусти <KEY>». Фраза «возьми …» может
принадлежать личному скиллу автономной работы. Услышав её в чате диспетчера, задать вопрос из §1, а не
запускать сразу.
1. **Лимит:** активных сессий задач ≤ 3, при перегрузке — 2. Планировщик тоже считается.
   Признаки перегрузки:
   - `headroom.ps1` дал запас < 4 ГБ;
   - сессии падают;
   - Georgy говорит, что машина тормозит.

   Снижение лимита записать на доску с причиной.
2. **Worktree:** командой `wt-new.sh` из профиля. Ветка — короткое имя `<KEY>-NN`, без трекинга `origin/main`:
   случайный `git push` не уйдёт в main.
3. **Сессия:** `start_session`:
   - `initiation: "user_asked"`, `context: "fresh"`;
   - `cwd` = worktree, `use_worktree: false`;
   - заголовок `<ветка> — <суть>`;
   - `prompt` = заполненный `brief.md`;
   - модель — как скажет Georgy (по умолчанию модель диспетчера).
4. **Один режим разрешений.** Диспетчер и все сессии задач работают в одном режиме разрешений, и это не
   bypassPermissions. Иначе сообщения между ними удерживаются, а в десктопе удержанное пропадает через 5 минут.
   Сразу после старта проверить режим новой сессии (`get_session`). Если он отличается — сказать Georgy и
   выровнять с его согласия.
5. Записать сессию на доску: ключ, ветка, база, касания, id сессии.
6. **Первая квитанция:** сессия отвечает «принял бриф». Нет ответа за 10 минут — см. «Протокол сообщений».

## 4. Очередь ресурсов

Профиль делит работу на три вида:
- **тяжёлое** — строго одно на всех, только с разрешения;
- **среднее** — по одному, разрешение короткое, без замера памяти, если запас ≥ 6 ГБ;
- **лёгкое** — без очереди.
1. Сессия пишет: «Прошу <ресурс> на ~N мин: <зачем>».
2. Диспетчер запускает `headroom.ps1` из профиля.
   - Ресурс свободен, запас ≥ 4 ГБ, порты свободны → «Разрешаю <ресурс>. Ответь «принял». Закончишь —
     останови свои серверы и напиши «освободил <ресурс>»». Записать на доску держателя и время.
   - Занят → поставить в очередь (FIFO; вперёд — то, что блокирует пуш). Ответить: «ты N-я, делай лёгкое».
   - Запас < 4 ГБ или неясный приоритет → спросить Georgy.
3. Пока тяжёлое выдано, `headroom.ps1` повторять при каждом отчёте любой сессии. Запас упал ниже 4 ГБ —
   попросить сессии без ресурса приостановить среднее и сказать Georgy.
4. После «освободил» — снова `headroom.ps1`. Порт ещё занят — сказать держателю. Затем выдать ресурс следующему.
5. **Держатель молчит или упал:**
   - заявленное время плюс 30 минут без вестей — спросить статус (с квитанцией);
   - сессия завершилась или не отвечает на повтор — спросить Georgy;
   - с его согласия погасить процессы по PID, которые назвал `headroom.ps1`, и вернуть ресурс в очередь.
6. **Миграции на дев-БД:** на доске всегда записано, чья миграция сейчас применена. Две ветки с разными
   новыми миграциями не получают дев-БД по очереди «как есть»: следующую пускать только после того, как
   Georgy решит, что делать с базой.

## 5. Вопросы, решения, согласия

- **Вопросы сессий** — собирать и приносить Georgy одним коротким списком (`AskUserQuestion`, если вопросов
  ≤ 4). Ответ передать сессии словами Georgy в кавычках. Сам за него не решать и не советовать там, где
  правило проекта это запрещает (вид пуша).
- **Согласия не передаются сообщением.** Claude Code не считает сообщение от другой сессии согласием
  пользователя. Пуш, MR, ответы в треды, запись в трекер и мутации дев-данных делаются одним из двух способов:
  - **(по умолчанию) делает диспетчер** по прямому ответу Georgy в своём чате:
    1. Сессия доложила «готово к пушу: <ветка> <sha>».
    2. Проверить, что `git -C <worktree> status --porcelain` пуст и `rev-parse HEAD` = sha из отчёта.
       Не совпало — стоп, спросить сессию.
    3. Спросить Georgy вид пуша (правило профиля).
    4. Пушить именно проверенный sha: `git -C <worktree> push … origin <sha>:refs/heads/<ветка>`.
    5. MR — по рецепту проекта, описание — из `memory/<ветка>/mr-desc.md`.
    6. Написать сессии: «запушено <sha>, MR !N».
  - **Georgy отвечает прямо в сессии задачи.** Диспетчер даёт ссылку: `[заголовок](#local_<id>)`.
- **Модель ревью** спрашивать у Georgy (правило хаба). Выбор модели — не согласие, его можно передать сообщением.

## 6. Конфликты между параллельными ветками

- После каждого отчёта, где появились новые коммиты, запускать `parallel-check.sh <repo> <база> <ветки волны…>`.
  `<база>` — общий родитель волны (ветка хребта), а не `origin/main`: иначе общие файлы хребта дают ложный шум.
  Нашёл конфликт — сразу сказать обеим сессиям, кто уступает. Если решить нельзя — нести Georgy.
- Перед пушем волны — **интеграционная проба** (тяжёлое) по рецепту в `slicing.md`. Делается во временном
  worktree `<KEY>-int`, а не в worktree сессии и не в основной копии.

## 7. Завершение

- **Сессия задачи:**
  - после пуша и MR (или по слову Georgy) написать ей: «Georgy: «закрывай». Вызови скилл wind-down»;
  - она пишет заметку, в которой есть раздел «Предлагаю в CLAUDE.md», и докладывает путь к ней;
  - предложения брать из заметки: строка отчёта обрезается;
  - архивировать сессию — только по «да» Georgy;
  - worktree убирать `wt-remove.sh` после мержа ветки и с согласия Georgy.
- **Сам диспетчер:** `/wind-down` в режиме диспетчера. Внести в CLAUDE.md проекта правила из разделов
  «Предлагаю в CLAUDE.md» заметок сессий и записать заметку партии. Память проектов локальная и не
  коммитится. Правку базы хаба коммитить только её путями и по слову Georgy.

## Протокол сообщений

- **Квитанции.** На каждое сообщение диспетчера с действием (бриф, «Разрешаю», «закрывай», вопрос о статусе)
  сессия отвечает «принял …». Нет квитанции за 10 минут — повторить один раз. Снова нет — проверить сессию
  (`get_session`) и сказать Georgy. Время отправки и квитанции — на доске.
- Каждый ход сессии задачи начинается строкой `Статус: … | Ждёт: … | Дальше: …`: диспетчер видит ~400 символов
  её отчёта. Подробности — `get_session` или сообщение ей.
- Диспетчер пишет сессиям коротко и по делу; адрес — `local_…` id с доски.
- Слэш-команды в сообщениях не исполняются: писать «вызови скилл wind-down», а не «/wind-down».

## Не делать

- Не запускать сессию без слова Georgy и не решать за него развилки.
- Не грепать код самому: подробности даёт сессия.
- Не давать двум параллельным сессиям одну горячую точку (`slicing.md`).
- Не держать очередь «в голове»: каждое изменение сразу заносить на доску.
- Не считать «закончено» по отчёту сессии: проверить ветку (`git log`, sha) и сам MR.
