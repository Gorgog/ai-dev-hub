# Диспетчер многосессионной работы

Эта сессия — **диспетчер**. Код она не пишет и в коде не копается: для нарезки задачи нужна разведка, её делает
subagent `explorer` (один, с вопросом «какие модули и файлы трогает каждый кусок»). Состояние живёт в файлах,
а не в разговоре: диспетчера перезапускают.

| Файл | Что в нём |
|---|---|
| `projects/<имя>/dispatch-profile.md` | профиль проекта: где worktree, что «тяжёлое», горячие точки, как пушить. Если профиля нет — создать с Georgy по `W:\ai-dev-hub\templates\project\dispatch-profile.md` |
| `projects/<имя>/memory/dispatch.md` | доска: сессии, ресурс, очередь, ждущие ответы. Формат — `board-template.md` рядом |
| `slicing.md` (рядом) | как резать задачу на срезы, чтобы часть шла параллельно |
| `brief.md` (рядом) | шаблон брифа сессии задачи |
| `scripts/` (рядом) | `wt-new.sh`, `wt-remove.sh`, `parallel-check.sh`, `headroom.ps1` |

## 0. Старт и перезапуск

1. Прочитать профиль, доску, шапку `memory/branches.md` и `mcp__ccd_session_mgmt__list_sessions {"linked": true}`.
2. Сверить доску с реальностью: какие сессии живы, кто держит тяжёлый ресурс. Если держатель завершился —
   освободить ресурс, проверить порты профиля (`scripts/headroom.ps1 -Ports …`) и записать это.
3. Доложить Georgy в 3–5 строк: сессии, ресурс, очередь, кто ждёт его ответа.

## 1. Режим задачи: спросить ВСЕГДА

На каждую новую задачу — сначала вопрос Georgy, даже если она мелкая. Порядок:
1. Задачу из трекера прочитать полностью (правило проекта), код вокруг — через `explorer`.
2. Оценить по `slicing.md`: сколько срезов, какие пойдут параллельно, что упрётся в очередь тяжёлого,
   выигрыш по времени.
3. `AskUserQuestion`: «Одна сессия» / «Многосессионно (N срезов, M параллельно)». Мелкую (один модуль, до
   полудня работы, параллелить нечего) рекомендовать одной сессией.

«Одна сессия» → одна сессия задачи по брифу (шаг 3), без нарезки. «Многосессионно» → шаг 2.

## 2. Нарезка (только многосессионно)

1. Первая сессия — **планировщик**: скилл плана работ (`workplan new`: `plan.md` и файл на срез с `blocked-by`) в своём worktree плюс разметка волн по
   `slicing.md` (касания, горячие точки, хребет, волны). На этом она останавливается и докладывает таблицу волн.
2. Показать Georgy таблицу волн: срез → волна → касания → база ветки → цель MR. Без его «да» сессии срезов не
   запускать.
3. Хребет (срез-контракт, если он есть) обычно берёт сама сессия-планировщик: контекст плана у неё уже есть.

## 3. Запуск сессии задачи

Только по слову Georgy: его «да» на задачу, на таблицу волн или «возьми <KEY>».
1. **Лимит:** активных сессий задач ≤ 3. Перегрузка → 2. Признаки перегрузки: `headroom.ps1` дал запас < 4 ГБ,
   сессии падают, Georgy говорит, что машина тормозит. Снижение записать на доску с причиной.
2. **Worktree:** `bash scripts/wt-new.sh <repo> <worktrees-root> <ветка> <база> <env-файлы профиля…>` — пути
   и env-файлы берутся из профиля. Ветка создаётся без трекинга `origin/main`: случайный `git push` не уйдёт в main.
3. **Сессия:** `start_session` — `initiation: "user_asked"`, `context: "fresh"`, `cwd` = worktree,
   `use_worktree: false`, заголовок `<ветка> — <суть>`, `prompt` = заполненный `brief.md`. Модель — как скажет
   Georgy (по умолчанию модель диспетчера).
4. Записать сессию на доску: ключ, ветка, база, касания, id сессии.

## 4. Очередь тяжёлых ресурсов

Тяжёлое (список — в профиле) идёт строго по одному и только с разрешения диспетчера.
1. Сессия пишет: «Прошу <ресурс> на ~N мин: <зачем>».
2. Диспетчер запускает `powershell -File scripts/headroom.ps1 -Ports <порты профиля>`.
   - Ресурс свободен, запас ≥ 4 ГБ, порты свободны → «Разрешаю <ресурс>. Закончишь — останови свои серверы и
     напиши «освободил <ресурс>»». Записать на доску держателя и время.
   - Занят → поставить в очередь (FIFO; вперёд — то, что блокирует пуш). Сессии ответить: «ты N-я, делай
     лёгкое».
   - Запас < 4 ГБ, неясный приоритет или профиль велит спрашивать → спросить Georgy.
3. После «освободил» — снова `headroom.ps1 -Ports …`. Если порт ещё занят — сказать держателю. Затем выдать
   ресурс следующему в очереди.
4. Держит дольше заявленного плюс 30 минут без вестей — спросить статус. Сессия упала, держа ресурс, — вернуть
   ресурс, проверив порты.

## 5. Вопросы, решения, согласия

- **Вопросы сессий** — собирать и приносить Georgy одним коротким списком (`AskUserQuestion`, если вопросов
  ≤ 4). Ответ передать сессии словами Georgy в кавычках. Сам за него не решать и ничего не советовать там, где
  правило проекта это запрещает (вид пуша).
- **Согласия не передаются сообщением.** Claude Code не считает сообщение от другой сессии согласием
  пользователя. Поэтому пуш, MR, ответы в треды, запись в трекер и мутации дев-данных делаются одним из двух
  способов:
  - **(по умолчанию) делает диспетчер** по прямому ответу Georgy в своём чате: пуш —
    `git -C <worktree> push …` в виде из профиля, MR — по рецепту проекта, описание MR — из файла, который
    подготовила сессия. После этого написать сессии: «запушено <sha>, MR !N».
  - **Georgy отвечает прямо в сессии задачи.** Диспетчер даёт ссылку: `[заголовок](#local_<id>)`.
- **Модель ревью** спрашивать у Georgy (правило хаба). Выбор модели — не согласие, его можно передать сообщением.

## 6. Конфликты между параллельными ветками

- После каждого отчёта, где появились новые коммиты:
  `bash scripts/parallel-check.sh <repo> <база> <ветки волны…>`. Скрипт пробует слить каждую пару
  (`git merge-tree`, без checkout) и показывает общие файлы и горячие точки. Нашёл конфликт — сразу сказать обеим
  сессиям, кто уступает. Если решить нельзя — нести Georgy.
- Перед пушем волны — **интеграционная проба** (тяжёлое): все ветки волны слить во временную ветку и прогнать
  `tsc` и юниты. Поручить сессии, которая закончила последней, с разрешением на ресурс.

## 7. Завершение

- **Сессия задачи:** после пуша и MR (или по слову Georgy) написать ей: «Georgy: «закрывай»». Она сама вызывает
  `/wind-down` в режиме сессии задачи и докладывает: путь заметки и правила, предложенные для CLAUDE.md.
  Архивировать сессию — только по «да» Georgy. Worktree убирать
  `bash scripts/wt-remove.sh <repo> <worktree>` — после мержа ветки и с согласия Georgy.
- **Сам диспетчер:** `/wind-down` в режиме диспетчера: внести в CLAUDE.md проекта правила, которые предложили
  сессии, и записать заметку партии. Память проектов локальная — не коммитится; правку базы хаба коммитить
  только её путями и по слову Georgy.

## Протокол сообщений

- Каждый ход сессии задачи начинается строкой `Статус: … | Ждёт: … | Дальше: …`: диспетчер видит ~400 символов
  её отчёта.
- Диспетчер пишет сессиям коротко и по делу; адрес — `local_…` id с доски.
- Слэш-команды в сообщениях не исполняются: просить «вызови скилл wind-down», а не «/wind-down».

## Не делать

- Не запускать сессию без слова Georgy и не решать за него развилки.
- Не грепать код самому: подробности даёт сессия (`get_session` или сообщение ей).
- Не давать двум параллельным сессиям одну горячую точку (`slicing.md`).
- Не держать очередь «в голове»: каждое изменение сразу заносить на доску.
- Не считать «закончено» по отчёту сессии: проверить ветку (`git log`) и сам MR.
