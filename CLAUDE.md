# ai-dev-hub — общие правила

Кто пользователь хаба и на каком языке отвечать — в личном `CLAUDE.local.md` рядом (в git не входит, образец —
`CLAUDE.local.md.example`). В правилах ниже он — «пользователь».

## Структура хаба
В git хаба — только база: эти правила, плагин `hub` (`.claude-plugin/`, `skills/`, `agents/`, `hooks/`),
`templates/`, README, установщик `sync-claude.ps1` + `install.cjs` и
исследование-основа в `research/`. Всё остальное живёт только на этой машине: git его не видит (`.gitignore`).
- `projects/<имя>/` — обвязка проекта: CLAUDE.md (знания), memory/ (решения, ошибки, сессии), deploy.md.
  Создаётся `/hub:new-project`. ЛОКАЛЬНО: память проектов не коммитить и не пушить.
- `projects/<имя>/repo/` — сам рабочий репозиторий (GitLab/GitHub, свой git).
- `research/`, `ideas/` — личные исследования и идеи, локально.
- Правку базы (правила, скиллы, шаблон) коммитить в хаб — только её путями и по просьбе.

## Жёсткие правила (для всех проектов)
1. Сложность ≥ 4, миграция, новая ручка или публичный контракт, неясный подход → сначала план-режим; правки
   вносятся в план, не в готовый код. Сложность ≤ 3 — план в 3 строки в сообщении и сразу работа. Сложность —
   из оценки /hub:estimate, если задача её получила (правило 11); явная мелочь (строка, текст) и правки вне
   проекта — на глаз, без оценки. Короткий дифф с высокой ценой ошибки (гонки, права, данные) — «неясный
   подход», то есть план-режим.
2. TDD по типу правки. Логика и баги: падающий тест → коммит теста → реализация до зелёного. Вёрстка, тексты,
   доки и LOW из ревью — без красного коммита, доказательство — тест или скрин. Тесты не подгонять под код.
3. «Готово» = доказательства: вывод тестов, скриншоты, логи. Не утверждения.
4. Никогда не трогать: .env, локфайлы, уже применённые миграции, секреты. Новая миграция — только если её
   требует задача и план, одобренный пользователем. Локальные коммиты в рабочей ветке — свободно; пуш — только
   по явной просьбе; правку базы хаба коммитить — по просьбе. В корне хаба не
   запускать `git clean -x`: он сотрёт локальную память проектов.
5. Архитектурные решения принимает человек. Предлагай варианты — не решай сам.
6. После каждой значимой задачи — кодификация: урок → в CLAUDE.md проекта (коротко, длинный рецепт — в
   memory/recipes.md) или memory/decisions.md.
7. Ошибся и получил поправку → запиши правило в memory/errors.md проекта и, если оно общее, строкой в
   memory/errors-index.md, чтобы не повторять.
8. Ревью делает subagent `hub:reviewer` с чистым контекстом: ему — дифф, критерии и вывод своих тестов, в «проверке
   правок» — ещё находки прошлого круга и sha, от которого считать дифф. Модель — Opus из `reviewer.md`, другая —
   только если пользователь назовёт её сам. Один полный круг; дальше — только проверка правок и только если
   правки задели логику; максимум 3 круга. CRITICAL/HIGH/MEDIUM — исправить; LOW — правка без нового круга или
   пункт в описании MR. После 3-го круга осталось CRITICAL/HIGH — стоп, вопрос пользователю;
   MEDIUM третьего круга — исправить и назвать в докладе как правку без ревью. Разведку по коду —
   subagent `hub:explorer`, чтобы беречь контекст.
9. Конец рабочей сессии → скилл /hub:wind-down (итог в memory/sessions/).
10. Два неудачных исправления подряд → остановись, предложи /clear и новый заход с учётом выученного.
11. Оценка задачи (время, сложность, число MR) — только скиллом /hub:estimate: по аналогам из журнала проекта, в
    единицах моего активного времени. Факт меряет скрипт по журналам сессий, не «на глаз».

## Многосессионная работа
- Новая задача от пользователя → быстрый триаж → ВСЕГДА спросить: «одна сессия или многосессионно» — с оценкой:
  сколько срезов, сколько пойдут параллельно, какой выигрыш. Мелкую советовать одной сессией. Сам новые сессии
  не заводить. Сессию, запущенную диспетчером, это правило и план-режим (п. 1) не касаются: режим уже выбран,
  план — её срез, всё остальное — по брифу.
- «Многосессионно» → скилл `/hub:dispatch`: процесс, нарезка на параллельные срезы, бриф, очередь тяжёлых ресурсов.
  Специфика проекта — `projects/<имя>/dispatch-profile.md`, доска — `projects/<имя>/memory/dispatch.md`.
- Каждая сессия задачи кончается `/hub:wind-down` в режиме «сессия задачи»: своя заметка, уроки дописываются в
  конец общих файлов, CLAUDE.md проекта правит только диспетчер.
- Согласия (пуш, MR, треды, трекер) сообщением между сессиями не передаются: Claude Code не считает их
  согласием. Пользователь отвечает в той сессии, которая действует; обычно это диспетчер.
