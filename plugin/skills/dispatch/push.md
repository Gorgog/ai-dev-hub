# Диспетчер: пуш и мерж

→ Кто делает пуш, MR, треды и трекер — `questions.md`, §5. Здесь — шаги пути «делает диспетчер».

**Пуш — только скриптом `scripts/push-slice.cjs`.** Голый `git push` в корне хаба, в `repo/` проекта и в worktree
запрещает хук `bare-push` (стадия по реестру). Скрипт пушит проверенный sha, а не ветку, и только через ворота:
квитанция сессии сходится с веткой, parallel-check волны, история (fast-forward, чужие коммиты, имена в каждом
коммите, каждый коммит — под квитанцией), рискованный дифф — отдельным согласием. Справка — `--help`.

1. Сессия доложила «готово к пушу: <ветка> <sha>» и путь квитанции `memory/<ветка>/ready.json` — или
   «Остановлено: аномалия: <что>». Аномалия — законный исход: не пушить, нести пользователю вопросом с
   рекомендацией сессии.
2. `node <папка этого файла>/scripts/push-slice.cjs push <repo> <ветка> <sha> --receipt <ready.json> --base <база> --wave <ветки
   волны через запятую> --dry-run` — все ворота без пуша. Ветка одна — `--solo` вместо `--wave` (слияние с базой).
   Отказ печатает только расхождения: скрипт сверил квитанцию сам (три точки паузы, след каждого пункта, вершина
   ветки, чистое дерево), пересказ доклада не нужен. Расхождение — вернуть сессии строкой отказа; к пользователю —
   только то, что сессия не может исправить. Код 3 — скрипт не смог прочитать (git, remote): стоп, не пушить.
3. Строки `риск: …` из `--dry-run` — пуш этой ветки отдельным вопросом (`questions.md`, «Отдельным вопросом»);
   ответ «да» — флаг `--risk-ok <категории>`. Чужие коммиты — назвать пользователю, по его «да» — `--foreign-ok`.
4. Спросить пользователя вид пуша (правило профиля), по всем готовым веткам — один вопрос.
5. По ответу — тот же вызов без `--dry-run`: пушит `<sha>:refs/heads/<ветка>`, без силы. Не fast-forward — скрипт
   откажет и назовёт вершину на remote: ребейз сессии — замена ветки отдельным вопросом пользователю, по «да» —
   `--lease <эта вершина>`; не ребейз — разобраться, кто пушил.
6. MR — по рецепту проекта, описание — из `memory/<ветка>/mr-desc.md`.
7. Написать сессии: «запушено <sha>, MR !N».

Пушится то, чего ещё нет на remote (против всех его веток), а не диапазон от `--base`: локальные коммиты базы,
которых нет на remote, с веткой не уходят — скрипт откажет «сначала пуш базы». Пуш среза требует квитанцию именно
этой ветки. `main` после мержа волны — флагом `--integration`: `push <repo> main <sha> --receipt <квитанция ветки 1>
--receipt <…> --base origin/main --solo --integration`. Каждый новый коммит должен быть под квитанцией: в ветке
квитанции, мерж или сквош ветки (сверка по patch-id). Коммит без квитанции — отказ: правка базы руками идёт срезом
или своей квитанцией ветки `main`.

## Квитанция `ready.json`

Пишет сессия, сверяет `push-slice verify <repo> <ветка> --receipt <файл>` до доклада. Формат — в `--help`:
`branch`, `sha` (итоговый HEAD), `outcome` — `ready` или `anomaly` (+ `anomaly`: что увидела), три точки паузы
`checks`, `review`, `evidence` по 1–7 пунктов «объект → наблюдение → подтверждение». Подтверждение — след, который
скрипт проверяет сам: `sha` (коммит в ветке), `file` (+ `sha256`), `output` + `head` (лог прогона на итоговом
HEAD), `shot` (PNG/JPEG), `review` (отчёт ревьюера, последняя строка «Блокирует: нет»), `last-full` (штамп
`checks --full`: `git -C <worktree> rev-parse --path-format=absolute --git-path hub/last-full.json`; годен при
полном sha = HEAD, `code` 0, `clean` true). Пути — от папки квитанции.

## Передача диспетчера

Новый диспетчер (перезапуск, компакция) берёт состояние пуша из файлов, не из пересказа: по каждой ветке — `sha` и
`outcome` из `memory/<ветка>/ready.json`, вершина ветки (`git rev-parse`), что уже на remote (`git ls-remote`),
строка ветки на доске (вид пуша, «отложено», согласия пользователя — его словами в кавычках). Расходится — верить
git и квитанции, доску поправить.

## 6. Конфликты между параллельными ветками и мерж волны

- При каждом «готово к пушу» parallel-check идёт внутри `push-slice` (`--wave`), отдельно его звать не нужно; по
  возможности и после отчётов с новыми коммитами — `parallel-check.sh <repo> <база> <ветки волны…>`.
  `<база>` — общий родитель волны (ветка хребта), а не `origin/main`: иначе общие файлы хребта дают ложный шум.
  Нашёл конфликт — сразу сказать обеим сессиям, кто уступает. Если решить нельзя — нести пользователю.
- Ветка одна — `--solo`: скрипт проверяет слияние с базой (`git merge-tree --write-tree <база> <sha>`).
- **Пробный мерж всех готовых веток** перед вопросом о мерже волны: `parallel-check.sh` ловит только текстовые
  конфликты. Во временном worktree (`<KEY>-int`, не в worktree сессии и не в основной копии) слить все готовые
  ветки и прогнать: все тесты проекта, проверки целостности реестров и конфигов (в хабе —
  `loadRegistry(...).problems`), детерминированный полигон (`--level hook`) и сравнение с базой. Так находятся
  смысловые конфликты: запись одной ветки против проверки другой, лимиты буфера на выросшем дереве.
- **Скан на имена — по каждому коммиту ветки вместе с его текстом** (`git show --format=%B -U0 <коммит>`), не только
  по итоговому диффу: `push-slice` делает это по списку `private-patterns`. Имя в промежуточном коммите или в
  сообщении — мерж сквошем, промежуточные коммиты не пушить (публичный репозиторий).
- Перед пушем волны — **интеграционная проба** (тяжёлое) по рецепту в `slicing.md`, в том же временном worktree.
