# Диспетчер: пуш и мерж

→ Кто делает пуш, MR, треды и трекер — `questions.md`, §5. Здесь — шаги пути «делает диспетчер».

1. Сессия доложила «готово к пушу: <ветка> <sha>».
2. Проверить, что `git -C <worktree> status --porcelain` пуст и `rev-parse HEAD` = sha из отчёта.
   Не совпало — стоп, спросить сессию. Цифры проверок в докладе должны быть с этого же HEAD (после последней
   правки ревью). Прогон начат раньше — повтор до пуша.
2a. `parallel-check.sh` по всем активным веткам — обязательно при КАЖДОМ «готово к пушу». В потоке сообщений
   «после каждого отчёта» забывается: в пилоте он прошёл только в конце.
3. Спросить пользователя вид пуша (правило профиля).
4. Пушить именно проверенный sha: `git -C <worktree> push … origin <sha>:refs/heads/<ветка>`.
5. MR — по рецепту проекта, описание — из `memory/<ветка>/mr-desc.md`.
6. Написать сессии: «запушено <sha>, MR !N».

## 6. Конфликты между параллельными ветками

- При каждом «готово к пушу» (обязательно, §5 п. 2a) и по возможности после отчётов с новыми коммитами —
  `parallel-check.sh <repo> <база> <ветки волны…>`.
  `<база>` — общий родитель волны (ветка хребта), а не `origin/main`: иначе общие файлы хребта дают ложный шум.
  Нашёл конфликт — сразу сказать обеим сессиям, кто уступает. Если решить нельзя — нести пользователю.
- Ветка одна (одна сессия под диспетчером) — `parallel-check.sh` сравнивать не с чем. Вместо него проверить
  слияние с базой: `git -C <repo> fetch origin && git -C <repo> merge-tree --write-tree origin/main <ветка>`
  (код 0 — чисто, 1 — конфликты, их файлы в выводе).
- Перед пушем волны — **интеграционная проба** (тяжёлое) по рецепту в `slicing.md`. Делается во временном
  worktree `<KEY>-int`, а не в worktree сессии и не в основной копии.
