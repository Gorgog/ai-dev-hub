# Диспетчер многосессионной работы

Эта сессия — **диспетчер**. Код она не пишет и в коде не копается. Разведку для нарезки делает один subagent
`explorer`: «какие модули и файлы трогает каждый кусок». Состояние живёт в файлах, а не в разговоре: диспетчера
перезапускают.

`<хаб>` — корень хаба; плагин `hub` — его папка `plugin/`. Скрипты — `<хаб>/plugin/skills/dispatch/scripts/`.
Готовые команды с путями проекта — в его профиле.

| Файл | Что в нём |
|---|---|
| `<хаб>/projects/<имя>/dispatch-profile.md` | профиль проекта: пути, тяжёлое и среднее, горячие точки, пуш, запрещённые сессиям скиллы. Нет профиля — создать с пользователем по `<хаб>/templates/project/dispatch-profile.md` |
| `<хаб>/projects/<имя>/memory/dispatch.md` | доска: сессии, ресурсы, очередь, квитанции, ждущие ответы. Формат — `board-template.md` рядом |
| `slicing.md` (рядом) | как резать задачу на срезы, чтобы часть шла параллельно; git-рецепты для веток срезов |
| `brief.md` (рядом) | шаблон брифа сессии задачи |
| `<хаб>/projects/<имя>/dispatch-rules.json` | что тяжёлое и среднее — для хука-замка. Образец — `<хаб>/templates/project/dispatch-rules.example.json`: скопировать в проект как `dispatch-rules.json` и поправить. Пока файла нет, замок в проекте не действует |
| `scripts/` (рядом) | `wt-new.sh`, `wt-remove.sh`, `parallel-check.sh`, `headroom.sh`, `hub-run.sh` (прогон в своей cgroup), `guard.cjs` (замок, его зовёт хук плагина), `grant.cjs` (разрешения) |

## 0. Старт и перезапуск

1. Прочитать профиль, доску, шапку `memory/branches.md` и `mcp__ccd_session_mgmt__list_sessions {"linked": true}`.
2. Сверить доску с реальностью:
   - какие сессии живы;
   - кто держит ресурсы;
   - чья миграция стоит в дев-БД.

   Если держатель завершился — см. §4, п. 5.
3. Доложить пользователю в 3–5 строк: сессии, ресурсы, очередь, кто ждёт его ответа.

## 1. Режим задачи: спросить ВСЕГДА

На каждую новую задачу от пользователя — сначала вопрос, даже если задача мелкая.
1. Задачу из трекера читает subagent: полностью, по правилам проекта. Он же смотрит код вокруг и возвращает
   выжимку — объём, модули, развилки. Сам диспетчер вложения и видео не читает: его контекст должен оставаться
   лёгким.
2. Оценить по `slicing.md`: сколько срезов, какие пойдут параллельно, что упрётся в очередь, выигрыш по времени.
   Время и сложность задачи и каждого среза — скиллом `estimate` (строки в журнал до запуска, без метки старта:
   её ставит сессия задачи). Факт среза — `session-time.cjs dir '<worktree>'`, если сессия метки не поставила.
3. `AskUserQuestion`: «Одна сессия» / «Многосессионно (N срезов, M параллельно)». Мелкую (один модуль, до
   полудня работы, параллелить нечего) рекомендовать одной сессией.

«Одна сессия» → одна сессия задачи по брифу (шаг 3), без нарезки. «Многосессионно» → шаг 2.

## 2. Нарезка (только многосессионно)

1. Первая сессия — **планировщик**. Она в своём worktree пишет план скиллом `workplan new` (`plan.md` и файл на
   каждый срез с `blocked-by`) и размечает волны по `slicing.md`: касания, горячие точки, хребет, волны. На этом
   она останавливается и докладывает таблицу волн.
2. Показать пользователю таблицу волн: срез → волна → касания → база ветки → цель MR. Без его «да» сессии срезов не
   запускать.
3. Хребет (срез-контракт, если он есть) обычно берёт сама сессия-планировщик: контекст плана у неё уже есть.

## 3. Запуск сессии задачи

**Слово запуска** — «да» пользователя на задачу или на таблицу волн, либо «запусти <KEY>». Фраза «возьми …» может
принадлежать личному скиллу автономной работы. Услышав её в чате диспетчера, задать вопрос из §1, а не
запускать сразу.

Слово запуска нужно **текстом в чате диспетчера** — сообщением пользователя или кнопкой next-step с готовым
текстом. Ответ в окне `AskUserQuestion` приложение для `start_session` не засчитывает: так было в пилоте 19.10,
когда диспетчера запустила другая сессия. Поэтому таблицу волн показать вопросом, а для запуска попросить
написать «запусти …».
1. **Лимит:** активных сессий задач ≤ 3, при перегрузке — 2. Планировщик тоже считается.
   Признаки перегрузки:
   - `headroom.sh` дал код 2 (запас < 4 ГБ) или 5 (давление памяти);
   - сессии падают;
   - пользователь говорит, что машина тормозит.

   Снижение лимита записать на доску с причиной.
2. **Worktree:** командой `wt-new.sh` из профиля. Ветка — короткое имя `<KEY>-NN`, без трекинга `origin/main`:
   случайный `git push` не уйдёт в main.
3. **Сессия:** `start_session`:
   - `initiation: "user_asked"`, `context: "fresh"`;
   - `cwd` = worktree, `use_worktree: false`;
   - заголовок `<ветка> — <суть>`;
   - `prompt` = заполненный `brief.md`;
   - модель — как скажет пользователь (по умолчанию модель диспетчера).
4. **Один режим разрешений.** Диспетчер и все сессии задач работают в одном режиме разрешений, и это не
   bypassPermissions. Иначе сообщения между ними удерживаются, а в десктопе удержанное пропадает через 5 минут.
   Сразу после старта проверить режим новой сессии (`get_session`). Если он отличается — сказать пользователю и
   выровнять с его согласия.
5. Записать сессию на доску: ключ, ветка, база, касания, id сессии.
   **Учёт времени** — как велит профиль. Сам диспетчер внешних систем учёта не открывает: в пилоте 19.10
   классификатор режима auto запретил ему это как действие в реальном мире. Таймеры ведёт пользователь.
6. **Первая квитанция:** сессия отвечает «принял бриф». Нет ответа за 10 минут — см. «Протокол сообщений».

## 4. Очередь ресурсов

Профиль делит работу на три вида:
- **тяжёлое** — строго одно на всех, только с разрешения;
- **среднее** — по одному, разрешение короткое; без нового замера памяти, если тяжёлого сейчас нет и последний
  `headroom.sh` дал 0, рядом с тяжёлым — замер обязательно;
- **лёгкое** — без очереди.

**Очередь держит механизм, а не уговор.** Замок `guard.cjs` (его функцию `decide()` вызывает PreToolUse-хук
плагина `hub`, `plugin/hooks/pretool.cjs`) перед каждой командой сессии из `projects/*/worktrees/*`
сверяет её с `<хаб>/projects/<имя>/dispatch-rules.json`. Команду тяжёлого или среднего он блокирует, пока в
`memory/dispatch-grants.json` нет разрешения этому worktree. Разрешение пишет только диспетчер:
`node <скрипты>/grant.cjs <папка проекта> grant <heavy|medium> <worktree> <минут> "<что>"`, снимает —
`… release <heavy|medium> <worktree>`, смотрит — `… show`. Разрешение истекает само: срок ставить с запасом.
Если правило блокирует безобидное или пропускает тяжёлое — поправить `dispatch-rules.json` и раздел
«Ресурсы» профиля вместе.

**Тяжёлое и среднее — в своей cgroup.** Сессия запускает их через
`bash <скрипты>/hub-run.sh <worktree>-<что> -MemoryMax <потолок из профиля> [-Timeout <с>] -- <команда>`
(дев-сервер в фоне — так же, `run_in_background`). Потолок убивает только этот прогон, а не десктоп или соседнюю
сессию; CPU-вес ниже, чем у десктопа и сессий. Код выхода — код команды; 137 — убит потолком памяти, 124 —
таймаут, причина строкой `hub-run: …`. Диспетчер видит прогоны в `hub-run.sh --list` (память сейчас / пик /
потолок, CPU, время), а кто сколько ест по worktree — в `headroom.sh -Worktrees <папка worktrees>`. `checks`
запускает свои шаги через `hub-run.sh` сам.

**Коды `headroom.sh`:** 0 — можно выдавать; 2 — запас (доступная память + свободный swap/zram) < `-MinGB`;
5 — давление памяти (PSI: `full avg10` ≥ 2 % или `some avg60` ≥ 10 % — ядро уже тормозит задачи, освобождая память,
сколько бы ГБ ни было «свободно»); 3 — порт занят или не проверен; 4 — доступной физической < `-MinPhysGB`.
Причин несколько — код первой из 2, 5, 3, 4; строки печатаются все, строка PSI — всегда.

1. Сессия пишет: «Прошу <ресурс> на ~N мин: <зачем>».
2. Диспетчер запускает `headroom.sh` из профиля.
   - Ресурс свободен, код 0 → `grant.cjs … grant` на
     заявленное время плюс 15 минут, затем сообщение: «Разрешаю <ресурс>. Ответь «принял». Закончишь —
     останови свои серверы и напиши «освободил <ресурс>»». Записать на доску держателя и время.
   - Занят → поставить в очередь (FIFO; вперёд — то, что блокирует пуш). Ответить: «ты N-я, делай лёгкое».
   - Код 2 или 5 → не выдавать: посмотреть `headroom.sh -Worktrees`, кто ест, и спросить пользователя. Неясный
     приоритет — тоже спросить.
   - Код 4 (доступной физической памяти < 1 ГБ) → тяжёлое можно выдать только одно, среднее параллельно с ним —
     нет. Запас с swap/zram при этом может быть большим: в пилоте 19.10 было 12 ГБ запаса и 0,5 ГБ физической.
3. Пока тяжёлое выдано, `headroom.sh` повторять при каждом отчёте любой сессии. Код 2 или 5 —
   попросить сессии без ресурса приостановить среднее и сказать пользователю.
4. После «освободил» — `grant.cjs … release`, снова `headroom.sh`. Порт ещё занят — сказать держателю.
   Затем выдать ресурс следующему. Просит продлить — новый `grant` тому же worktree.
5. **Держатель молчит или упал:**
   - заявленное время плюс 30 минут без вестей — спросить статус (с квитанцией);
   - сессия завершилась или не отвечает на повтор — спросить пользователя;
   - с его согласия погасить прогоны держателя целиком — `hub-run.sh --stop <worktree>` (всё дерево процессов,
     с воркерами); запущенное не через `hub-run.sh` (`preview_start`) — по PID порта из `headroom.sh`; затем
     вернуть ресурс в очередь.
6. **Миграции на дев-БД:** на доске всегда записано, чья миграция сейчас применена. Две ветки с разными
   новыми миграциями не получают дев-БД по очереди «как есть»: следующую пускать только после того, как
   пользователь решит, что делать с базой.

## 5. Вопросы, решения, согласия

- **Каждое решение пользователя — вопросом с вариантами** (`AskUserQuestion`), а не вопросом прозой в конце
  сообщения. Исключение — слово запуска, оно нужно текстом (§3).
- **Вопросы сессий** — собирать и приносить пользователю одним пакетом, у каждого вопроса — рекомендация сессии.
  В пилоте на 20 вопросов хватило одного ответа «рекомендации сессий». Больше 4 вопросов — списком текстом и
  вопрос «принять рекомендации / ответить по пунктам». Ответ передать сессии словами пользователя в кавычках. Сам за него не решать и не советовать там, где
  правило проекта это запрещает (вид пуша).
- **Согласия не передаются сообщением.** Claude Code не считает сообщение от другой сессии согласием
  пользователя. Пуш, MR, ответы в треды, запись в трекер и мутации дев-данных делаются одним из двух способов:
  - **(по умолчанию) делает диспетчер** по прямому ответу пользователя в своём чате:
    1. Сессия доложила «готово к пушу: <ветка> <sha>».
    2. Проверить, что `git -C <worktree> status --porcelain` пуст и `rev-parse HEAD` = sha из отчёта.
       Не совпало — стоп, спросить сессию. Цифры проверок в докладе должны быть с этого же HEAD (после последней
       правки ревью). Прогон начат раньше — повтор до пуша.
    2a. `parallel-check.sh` по всем активным веткам — обязательно при КАЖДОМ «готово к пушу». В потоке сообщений
       «после каждого отчёта» забывается: в пилоте он прошёл только в конце.
    3. Спросить пользователя вид пуша (правило профиля).
    4. Пушить именно проверенный sha: `git -C <worktree> push … origin <sha>:refs/heads/<ветка>`.
    5. MR — по рецепту проекта, описание — из `memory/<ветка>/mr-desc.md`.
    6. Написать сессии: «запушено <sha>, MR !N».
  - **Пользователь отвечает прямо в сессии задачи.** Диспетчер даёт ссылку: `[заголовок](#local_<id>)`.
- **Модель ревью** — Opus из `reviewer.md` (правило 8 хаба); другую — только если пользователь назвал её сам. Выбор
  модели — не согласие, его можно передать сообщением.

## 6. Конфликты между параллельными ветками

- При каждом «готово к пушу» (обязательно, §5 п. 2a) и по возможности после отчётов с новыми коммитами —
  `parallel-check.sh <repo> <база> <ветки волны…>`.
  `<база>` — общий родитель волны (ветка хребта), а не `origin/main`: иначе общие файлы хребта дают ложный шум.
  Нашёл конфликт — сразу сказать обеим сессиям, кто уступает. Если решить нельзя — нести пользователю.
- Ветка одна (одна сессия под диспетчером) — `parallel-check.sh` сравнивать не с чем. Вместо него проверить
  слияние с базой: `git -C <repo> fetch origin && git -C <repo> merge-tree --write-tree origin/main <ветка>`
  (код 0 — чисто, 1 — конфликты, их файлы в выводе).
- Перед пушем волны — **интеграционная проба** (тяжёлое) по рецепту в `slicing.md`. Делается во временном
  worktree `<KEY>-int`, а не в worktree сессии и не в основной копии.

## 7. Завершение

- **Сессия задачи:**
  - после пуша и MR написать ей: «Диспетчер: пуш и MR сделаны — вызови скилл wind-down». Слова пользователя
    цитировать, только если он их сказал: по его «закрывай» — «Пользователь: «закрывай». Вызови скилл wind-down»;
  - она пишет заметку, в которой есть раздел «Предлагаю в CLAUDE.md», и докладывает путь к ней;
  - предложения брать из заметки: строка отчёта обрезается;
  - архивировать сессию — только по «да» пользователя;
  - worktree убирать `wt-remove.sh` после мержа ветки и с согласия пользователя.
- **Сам диспетчер:** `/hub:wind-down` в режиме диспетчера. Внести в CLAUDE.md проекта правила из разделов
  «Предлагаю в CLAUDE.md» заметок сессий и записать заметку партии. Память проектов локальная и не
  коммитится. Правку базы хаба коммитить только её путями и по слову пользователя.

## Протокол сообщений

- **Квитанции.** На каждое сообщение диспетчера с действием (бриф, «Разрешаю», «вызови скилл wind-down»,
  вопрос о статусе) сессия отвечает «принял …». Нет квитанции за 10 минут — повторить один раз. Снова нет — проверить сессию
  (`get_session`) и сказать пользователю. Время отправки и квитанции — на доске.
- Каждый ход сессии задачи начинается строкой `Статус: … | Ждёт: … | Дальше: …`: диспетчер видит ~400 символов
  её отчёта. Подробности — `get_session` или сообщение ей.
- Диспетчер пишет сессиям коротко и по делу; адрес — `local_…` id с доски.
- Время на доске — из `date`, не на глаз: в пилоте первые записи отставали на час.
- Сообщение может доходить несколько минут, пока у сессии идёт ход: это не потеря. Повтор — по правилу квитанций.
- Слэш-команды в сообщениях не исполняются: писать «вызови скилл wind-down», а не «/hub:wind-down».

## Не делать

- Не запускать сессию без слова пользователя и не решать за него развилки.
- Не грепать код самому: подробности даёт сессия.
- Не давать двум параллельным сессиям одну горячую точку (`slicing.md`).
- Не держать очередь «в голове»: каждое изменение сразу заносить на доску.
- Не считать «закончено» по отчёту сессии: проверить ветку (`git log`, sha) и сам MR.
