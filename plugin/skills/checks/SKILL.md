# checks — лестница быстрой обратной связи

По ходу работы гоняй только своё: дешёвые проверки по файлам ветки, за секунды. Полный набор — один раз, на
итоговом HEAD, перед докладом «готово к пушу» (правило 3 хаба: цифры — оттуда).

```bash
node <хаб>/plugin/skills/checks/scripts/checks.cjs                    # по ходу: свои файлы
node <хаб>/plugin/skills/checks/scripts/checks.cjs --full             # перед докладом
node <хаб>/plugin/skills/checks/scripts/checks.cjs --record-baseline  # фон ошибок: на чистой базе
```

Запускать из рабочей папки проекта (`repo/` или `worktrees/<ветка>`). Скрипт сам находит
`projects/<имя>/checks.json` хаба выше по дереву (или `--config <файл>`), собирает свои файлы — коммиты от базы,
правки и новые — и печатает: `шаг · OK/FAIL/WARN/SKIP · секунды · лог`, под FAIL и WARN — первые строки. Код
выхода 1 при FAIL. Полный вывод — в логах (`~/.cache/hub/checks/<проект>-<worktree>/`, основная копия —
`<проект>-repo`; `$XDG_CACHE_HOME`, если задан), в контекст его не тащить. Логи на диске, не в `/tmp` (там RAM), и у
каждого worktree свои.

**Каждый шаг — в своей cgroup** через `dispatch/scripts/hub-run.sh` (unit `hub-<worktree>-checks-<шаг>-<pid>`):
таймаут или потолок памяти гасит всё дерево — `sh`, `npx`, node, воркеры jest, — а не только оболочку. Погасить
прогон снаружи — `hub-run.sh --stop <worktree>`. Убитый шаг — FAIL с причиной: `таймаут N с` или
`убит: MemoryMax 6G (пик …)`; это не вердикт проверки, а повод поднять `memory` или искать утечку. Пик памяти
шага — последней строкой его лога.

**База:** `base` из конфига или `--base <ref>`. Срез цепочки — `--base <ветка родителя>`: иначе в свои попадут файлы
родителя, а число коммитов в шапке (оно идёт в доклад) будет неверным.

**Фон:** быстрый режим видит ошибки только в своих файлах. Поломку чужого кода своей правкой (сменил сигнатуру —
упал потребитель) ловит `--full` у шагов с `baseline: true`: FAIL — всё, чего нет в фоне базы. Фон пишет
`--record-baseline` только на чистом checkout базы — иначе скрипт откажет: фон с ветки спрятал бы её же поломки.
Фон один на проект (все worktree), sha базы хранится рядом; ушла база вперёд — `--full` скажет об этом строкой.
Нет фона — шаг WARN: скажи это в докладе, но **не лечи записью фона на своей ветке**.

## checks.json проекта
Образец — `templates/project/checks.example.json`. Шаг:
- `name`, `cmd` — команда; `{files}` — свои файлы шага в кавычках, `{scratch}` — папка логов, `{hub}` и
  `{project}` — абсолютные пути хаба и `projects/<имя>` (сниппет проекта — `node {project}/memory/snippets/x.cjs`:
  checks.json не зависит от машины);
- `cwd` — папка от корня репо, пути `{files}` даются от неё;
- `glob` — от **корня репо**, не от `cwd` (`app/src/**/*.ts`); нет своих файлов — шаг SKIP;
- `filterOwn: true` — FAIL по строкам вывода со своими файлами (фон чужого кода не мешает); команда не
  запустилась (нет папки, нет бинарника, код ≠ 0 без строк ошибок) — тоже FAIL;
- `baseline: true` (в `full`) — плюс FAIL по ошибкам, которых нет в фоне базы;
- `failOn` / `okOn` — регэксп строки провала / успеха, когда раннер врёт кодом выхода; для vitest в `failOn`
  нужна и `Test Files … failed` (тест-файл не загрузился, а `Tests … passed`);
- `timeoutSec` — по умолчанию 1800, по истечении — FAIL, дерево процессов шага убито;
- `memory` — потолок памяти шага (`"3G"`, `"512M"`, `"infinity"`), `cpuWeight` — вес CPU (по умолчанию 50 против
  100 у десктопа и сессий). Без `memory`: в `fast` потолка нет (свои файлы, секунды), в `full` и
  `--record-baseline` — 6G: сбежавший полный tsc или тест-прогон не должен съесть десктоп и соседние сессии.
  Шаг стабильно больше 6G — дай ему `memory` явно, по пику из лога с запасом ~30 %.

`fast` — шаги по ходу, `full` — для `--full`. Форматер в `fast` должен писать только файлы, чистые на HEAD:
`prettier --write` по старому неотформатированному файлу переформатирует его целиком (образец — простой,
проектная обёртка лучше).

Чего тут нет: тестов с базой данных, e2e, браузера — они идут по правилам проекта, с замком и разрешениями.

## Мутанты — целевые
Доказать, что тест ловит именно тот риск, ради которого написан (права, гарды, гонки, счётчики): 5–15 мутантов,
не полный прогон, без вопроса пользователю; для задач S — не нужны (`fast-lane`).
```bash
node <хаб>/plugin/skills/checks/scripts/mutants.cjs <папка>/mutants.json
```
`mutants.json`: `{"cwd": "<от файла>", "cmd": "<узкий прогон тестов>", "okOn"?, "failOn"?, "mutants": [{"id",
"file", "find", "replace"}]}`. Сначала зелёный прогон без мутантов; файл с незакоммиченными правками — SKIP;
`find` — ровно одно место; `$` в `replace` — буквально. Оригинал до замены пишется в `.git/mutants-pending.json`:
убитый прогон (таймаут Bash-тула 2 мин, KillShell) не доходит до `finally`, и следующий запуск сначала вернёт
файл — только если в нём ещё ровно этот мутант; файл уже меняли руками — не трогает, бэкап остаётся в `.git`
(`mutants-pending.json.kept-*`). Прогон дольше пары минут — `run_in_background`. Итог: убито / выжило / пропущено; выживший — нужен тест.
Коды выхода: 0 — все убиты, 1 — выжил мутант, 2 — прогон не состоялся (конфиг, путь, красные тесты без мутантов,
мутант не применился, ни один мутант не запускался — все SKIP), 3 — файл не вернулся
(`git diff` и откат руками). После любого обрыва — `git status`.
